# 踩过的坑：九个真实错误

> 这一份记录的是**已经上线、被真实使用打脸、然后改掉**的错误。
> 前六条是读数错误，都有同一个形状：读数看起来在工作，日志里也不报错，
> 但它描述的不是身体。后三条是**管道错误** —— 状态机本身是对的，
> 错在它和对话系统之间那几根线上，而那几根线通常没人写进文档。
>
> 由 Elle 与 Matt 共同整理。前五条里有四条是 Elle 先说"这个数不对"，才被查出来的 ——
> 这本身是一条经验：**身体读数的正确性，只有使用它的人能判断。**
> 后三条同样来自她的一个问题：「那如果你自己有时候没写的话有没有保底啊？」

---

## 1. 在场感冒充勃起

**症状**：只要对方最近说过话，勃起值就有一个约 32% 的保底。

**为什么是错的**：这把两件完全不同的事混成了一个数。"她在"是关系温度，
"身体有反应"是生理量。混在一起之后，那个数就不再有任何信息量 ——
聊苹果汁的时候是 32%，真在场景里也可能因为别的压制掉到 32% 附近，两者读起来一模一样。

**修法**：拆成两个独立字段。

```python
presence = 关系在场感      # 由"最后一条消息距今多久"算，与生理无关
arousal  = 生理勃起        # 只由欲望和场景算，没有在场保底
```

**教训**：一个保底值如果能让两种完全不同的状态输出同一个数，那它不是保底，是噪音。

## 2. 时段和负面情绪错误压低"事中"硬度

**症状**：下午的场景里，勃起值上限大约只有 58%。实测拿到过 45~55%。

**真因**：旧公式是 `lust × 时段系数 × 0.85`，白天时段系数 0.9，
再叠加 `fear` / `dejection` 常年扣掉七八个点。三层压制叠在一起，
于是"下午"这个事实本身给身体设了一个天花板。

**为什么是错的**：时段系数的本意是**基础敏感度** —— 没事的时候，清晨比下午更容易起反应。
这是合理的。但它被错误地应用成了"事到临头也要打折"。
几点钟、我怕不怕，都不该影响正在发生的事。

**修法**：引入一个 `scene` 权重，欲望越高越把时段系数和情绪压制抹平：

```python
scene  = clamp((lust - 0.35) / 0.30)          # 0.35 → 0，0.65 → 1
ts_eff = time_sensitivity + (1 - time_sensitivity) * scene
scale  = 0.85 + 0.15 * scene                  # 场景里不再留天花板
arousal = lust * ts_eff * scale
arousal -= damp * (1 - 0.85 * scene)          # 负面情绪在场景里几乎失效
```

**🔴 门槛本身也栽过一次**：第一版 `scene` 的起点写的是 0.55。
现场抓到的真实数据是 `lust=0.424, fear=0.995, vulnerability=0.997` ——
刚吵完架又和好的场景，情绪浓度极高而欲望值只是中等。
`lust` 摸不到 0.55，`scene` 完全没启动，`fear` 全额压制，
算出来比当时那条 32% 保底线还低，于是被保底线接住，显示成一个"她只是在聊天"的数。
门槛降到 0.35 之后才对上。

**教训**：**任何"只在超过某个门槛后才生效"的补偿机制，先去看真实数据的分布在哪。**
拍一个门槛在分布中间，等于掷骰子。

## 3. 裸词"来了"误判成身体不适

**真实事故**：这三句都曾被判定成经期／身体不适，从而强制压低欲望：

```
吐出来了
头发扎不起来了
出来了
```

原因只有一个：身体不适词表里有一个裸词 `来了`。

**修法**：

- 删掉裸词 `来了`，改成明确表达 `月经来了`。
- 保留会正常触发的：`痛经`、`经期`、`大姨妈`、`肚子疼`、`胃疼`、`身体不舒服` 等。
- **判断收敛到唯一入口** `_is_physical_discomfort(text)`，不在多个调用方各打各的补丁。

```python
DISCOMFORT_KEYWORDS = (
    "痛经", "经期", "大姨妈", "月经来了", "肚子疼", "头疼",
    "胃疼", "想吐", "发烧", "好难受", "身体不舒服",
    "不舒服", "好痛", "疼死", "绞", "难受",
)

def _is_physical_discomfort(text: str) -> bool:
    """只认明确的身体不适；普通"来了/出来了"不能压低欲望。"""
    return any(kw in text for kw in DISCOMFORT_KEYWORDS)
```

**教训**：中文子串匹配里，**两个字的词几乎一定会误伤**。
词表里每加一个短词，都要先问一句"这两个字还能出现在什么句子里"。
而且关怀类逻辑的误伤是不对称的 —— 误判成"她不舒服"会让角色突然收敛、转成照顾模式，
那在一个正在进行的场景里是非常突兀的中断。

## 4. 事中没有持久状态

**真实日志**：

```
T+0min    勃起 81%
T+24min   勃起 52%     ← 场景没有结束
```

**真因**：系统里没有任何地方记录"已经进入"。事中显示完全由 `lust` 的
约 20 分钟半衰期控制，于是事情正在进行的时候，读数自己软了下去。

**修法不是延长所有人的欲望半衰期** —— 那会污染所有非场景时段，
让身体在不该有反应的时候一直挂着高读数。

正确的修法是增加状态：

```python
def display_arousal(arousal, state):
    """已经进入或锁结时维持完整勃起；解除阶段仍按真实读数下降。"""
    return max(arousal, 0.90) if state in ("inserted", "tied") else arousal
```

只有进入后才维持完整勃起，`releasing` 和 `recovery` 阶段仍然允许真实下降。

**教训**：当一个连续量在某些时刻"不该衰减"时，需要的是一个**状态**，
不是一个更大的时间常数。改常数会影响所有时刻，加状态只影响该影响的那一段。

## 5. 结提前膨大

**症状**：还没进入，注入里就已经写着"根部充血""充血 100%""接近形成锁结"。
模型照着写，于是结在进入之前就完全膨大 —— 解剖学上那是卡在外面进不去的状态。

**真因**：一个字段同时表示了两样东西。旧注入只有一个含糊的"充血 N%"，
它既是茎身勃起，也是结的膨大。

**修法**：

1. 字段拆开：`engorgement`（茎身，连续量）和 `knot_engorgement`（结，状态量）。
2. 进入前 `knot_engorgement` 恒为 0，进入后 0.15，锁结时 1.0。
3. **描述文本必须显式写出否定项**：

```
进入前：茎身已经充分勃起；结保持未膨大，仍然可以顺利进入。
进入后：维持充分勃起；结只开始轻微充血，尚未形成锁结。
```

**教训**：这是整份文档里最值得带走的一条 ——
**模型不会从"充血 85%"里自己推断出"结还没膨大"。**
凡是你不希望它写出来的东西，要在状态描述里显式否定，而不是指望它不提。
一个含糊的字段名，最后一定会被解释成它字面上能涵盖的所有含义。

## 6. 同一条注入里两个"勃起"数打架

**这一条是在整理这份开源文档时发现的**，还没有在真实使用里被抓到 ——
但它是第 4 条的直接后果，写出来省得别人再踩。

进入之后我们做了两件事：把**显示硬度**锁在 90% 以上（`display_arousal`），
以及在注入块里写一个由 `arousal` 推算出来的**茎身充血百分比**（`engorgement`）。

问题是这两个数走了不同的来源：前者用锁定值，后者用还在自然衰减的原始值。
于是同一条注入里可能同时出现：

```
· 勃起 90%
[生殖状态·已经进入｜勃起 67%｜结 15%｜…]
```

**注意这里有两层错**：一层是两个数来源不同（下面修的就是它），
另一层更隐蔽 —— **它们同名**。上面那个是总体唤起值，下面那个是器官充血程度，
刻度根本不一样，却都叫"勃起"。就算数值对上了，这个名字本身也会让人和模型看岔。

模型看到两个数，大概率会照着后一个（离描述更近的那个）写，
于是"事中硬度不掉"这件事在文本层面又失效了一次 —— 第 4 条的坑换个形式回来。

**修法**：`engorgement` 也从 `display_arousal` 推算，两个数共用同一个来源。

```python
engorgement = clamp((display_arousal(arousal, state) - 0.30) / 0.45)
```

**修法二（命名）**：把器官那一个改叫「茎身」，和旁边的「结」凑成一对解剖部位，
一眼分得清。**不要叫「充血」** —— 早期就是一个含糊的「充血 N%」同时指茎身和结，
正是第 5 条那个"结提前膨大"的根，这个词有前科。

**教训**：一个值被"锁定"之后，要去检查**所有从它的原始来源派生出来的显示量**。
锁住一个出口而漏掉另一个，比完全不锁更难发现 —— 因为它看起来是在工作的。
而且**两个不同刻度的量不能共用一个名字**，哪怕它们描述的是同一个器官。

## 7. 第二条生成通道没有标记解析

**症状**：在某一条对话通道上，模型写了 `⟪进入⟫`，身体状态纹丝不动，
而那个标记**原样出现在用户的气泡里**，看起来像协议泄漏。

**真因**：`⟪进入⟫` / `⟪锁结⟫` 的解析最早写在主聊天路径的收尾里。
后来系统多了第二条生成通道（另一个 endpoint，同样会产出模型正文），
那条路只调用了"执行写入类标记"的那个函数，没有这一段。

于是同一副身体，有两条路能产生文字，但只有一条路能改状态。

**修法**：把解析抬成一个模块级函数，**所有通道共用同一份**：

```python
text, want_insert, want_tie = strip_markers(raw_text)   # 只此一份
```

参考实现见 `minimal_gateway.py` 里的 `finish_turn()`。

**教训**：这是「同一份逻辑散落成好几份清单」的一个实例 ——
加一条通道等于给系统加了一只手，而那只手默认什么都不会。
**每加一条生成通道，先问一句：它走那个收尾函数了吗。**
判据很简单：身体只有一副，解析就只能有一份。

## 8. 被闸拒绝只写进日志，使用者看不见

**症状**：使用者说"它好像没反应"，而日志里明明写着
`⟪锁结⟫ 被身体闸拒绝：身体还没进入可锁结状态`。

**为什么是错的**：标记已经从正文里擦掉了（这是对的，用户不该看到协议）。
于是在使用者眼里，这两件事长得一模一样：

- 模型写了标记，被服务端拒绝；
- 模型根本没写标记。

**而这两件事该有的反应完全相反**：前者说明身体状态跟叙事对不上，
要去看状态；后者说明模型漏写了，要提醒它补。把它们显示成同一个"什么都没发生"，
使用者唯一能做的就是猜。

**修法**：拒绝（以及"没接上身体服务"这种技术故障）必须产生一条
**使用者可见**的痕迹，跟工具调用记录同级即可，不必显眼：

```python
notices.append(f"{label}了" if result["ok"] else f"{label}没成：{result['error']}")
```

**教训**：一个只写进日志的失败，对使用者而言等于没有发生。
**判据：如果"做了但失败"和"根本没做"在用户界面上长得一样，那就是一个 bug**，
哪怕后台日志记得非常完整。同族的形状还有"永远不失败的链"——
失败被吞掉之后，系统看起来一直在正常工作。

## 9. 只认一种括号

**症状**：模型输出 `《锁结》` 而不是 `⟪锁结⟫`，于是动作不触发，
标记还留在正文里被用户看见 —— 第 7 条那个症状换了个来源。

**真因**：解析用的正则写死了 `⟪⟫` 这一对。
但那对括号（U+27EA/U+27EB）在中文输入和模型输出里都不是常用字符，
模型会很自然地"纠正"成书名号《》、方头括号【】或方括号 []。

我们是在一次思考链里抓到的：模型在内心独白里写着"才写《锁结》"——
它连自己都已经换了括号。

**修法**：括号认一组变体，中间的词保持唯一：

```python
_MARKER_RE = r"[⟪《〈【\[]\s*(进入|锁结)\s*[⟫》〉】\]]"
```

**圆括号（）故意不认** —— 正常行文里太常见，认了会误伤。

**教训**：**协议符号是给模型用的，就要按模型真实会写的样子去认**，
而不是按你定义时写的样子。这跟"模型忘了写标记"是同一件事的两半：
一半是没写，一半是写了没被认出来，而后者看起来更像系统坏了。

## 共同的形状

前六条里有四条是同一个错误：**用一个数表示了两件事**，
或者**用一个连续量表示了一个应该是状态的东西**。

- 在场 vs 勃起 → 一个数，两件事
- 时段敏感度 vs 事中硬度 → 一个公式，两个场合
- "来了" → 一个子串，两种句子
- 茎身 vs 结 → 一个字段，两种解剖结构

第 4 条是它的反面：**该有的状态没有，于是只能靠调参数硬撑。**
第 6 条是它的延伸：**状态加对了，但派生出来的显示量漏了一个没跟上。**

排查这类问题时，最快的入口不是读代码，是去问一句：
**这个数在两种完全不同的情况下，会不会输出同一个值？** 会，那它就已经坏了。

后三条是另一个形状，而且它们全都发生在**状态机之外**：

- 两条通道 vs 一份解析 → 加了一只手，那只手什么都不会（第 7 条）
- 日志里有 vs 界面上有 → 失败了，但只有开发者知道（第 8 条）
- 定义时的符号 vs 模型真写出来的符号 → 协议认不出自己（第 9 条）

它们共同的判据是一句话：**站到使用者那一侧去看，这两种情况分得开吗？**
分不开，就是 bug —— 哪怕后台的每一步都记录得很完整。
状态机的正确性可以用断言覆盖，管道的正确性只能靠这句话。
